1. Обґрунтування простору станів та евристики

Простір станів для задачі Судоку визначається як:
- S₀: часткова сітка 9x9 з початковими значеннями (0 = порожня клітинка)
- Actions(S): розміщення допустимого числа (1-9) у порожню клітинку,
  де допустимість визначається обмеженнями рядка, стовпця та блоку 3x3
- Result(S,A): нова сітка з розміщеним числом
- GoalTest(S): усі клітинки заповнені, і кожен рядок/стовпець/блок
  містить числа 1-9 без повторень
- g(n): кількість розміщених чисел (кроків) від S₀ до n

Евристична функція h(n) для A*: 
  h(n) = кількість порожніх клітинок, що залишились
  АБО ∞, якщо існує клітинка з 0 кандидатів (тупикова гілка).
  Хоча ця евристична функція відображає мінімально можливий шлях, 
  потрібний для вирішення судоку, вона не є ефективною для вибору між різними гілками пошуку, 
  оскільки її значення залежить лише від кількості порожніх клітинок. 
  Тому для всіх вузлів, що знаходяться на однаковій глибині, 
  значення h(n) є однаковим, незалежно від того, які саме значення були обрані на попередніх кроках. 
  У результаті функція f(n) = g(n) + h(n) також не розрізняє такі гілки.

MRV (Minimum Remaining Values) — це стратегія вибору шляху для DFS, яка обирає найбільш обмежену клітинку. 
Це дозволяє зменшити кількість рекурсивних викликів та відкатів порівняно з довільним 
порядком вибору клітинок (як у звичайному DFS).

3. Аналіз пам'яті
Peak Memory (KB) зростає для A* порівняно з DFS/MRV (напр., ~31600 KB 
проти ~25300 KB в середньому), що пояснюється необхідністю зберігати 
кілька незалежних копій стану (grid + candidates dict) одночасно 
у черзі з пріоритетом, на відміну від DFS/MRV, які мутують єдину 
спільну структуру даних in-place.

Примітка: Max Frontier Size для DFS/MRV вимірює глибину рекурсії 
(проксі для розміру стеку викликів), тоді як для A* це реальний 
розмір черги з пріоритетом — ці значення не є прямо порівнюваними 
структурно, хоча обидва відображають пікове використання пам'яті 
відповідного підходу.

4. Admissibility test

Доведення допустимості h(n):

Нехай h*(n) — справжня мінімальна кількість кроків для завершення 
судоку зі стану n. Оскільки кожен крок заповнює рівно одну клітинку,
а завершений розв'язок вимагає заповнення всіх порожніх клітинок, то:

h*(n) ≥ (кількість порожніх клітинок у стані n)

Наша евристика h(n) = (кількість порожніх клітинок), отже:

h(n) ≤ h*(n) для будь-якого розв'язного стану n.

Умова допустимості виконується. Для тупикових станів (де існує 
клітинка з 0 кандидатів), h(n) = ∞, що коректно відображає 
відсутність розв'язку (h*(n) також не визначено/нескінченне).

5. Додаткова оптимізація: DFS + MRV + Hidden Singles + IndexedHeap

Окрім стандартних Backtracking DFS, Backtracking + MRV та A*, я реалізувала
додатковий алгоритм (позначений як`opt`), який розширює MRV-підхід у двох напрямках.

Hidden Singles. Під час пошуку клітинки з найменшою кількістю кандидатів 
(MRV) алгоритм додатково перевіряє рядок, стовпець та блок цієї клітинки на 
наявність hidden singles — цифр, які є єдиним можливим кандидатом у межах 
рядка, стовпця або блоку, навіть якщо сама клітинка формально має кілька 
кандидатів. Такі клітинки розставляються одразу, без додаткового розгалуження 
пошуку, що зменшує кількість вузлів, які потрібно дослідити.

Кастомна структура даних: IndexedHeap. Стандартний `heapq` у Python не 
підтримує зміну значення довільного елемента в купі — лише вставку та 
видалення мінімуму. Оскільки MRV-евристика та hidden singles вимагають 
постійного оновлення кількості кандидатів для клітинок після кожного 
розміщення цифри (у сусідніх клітинках кількість кандидатів зменшується), 
я реалізувала власну структуру `IndexedHeap`.

Ключова ідея — словник `position`, який зберігає індекс кожної клітинки 
`(row, col)` у масиві купи. Це дозволяє за O(1) знайти позицію довільної 
клітинки та виконати `update()` — змінити кількість кандидатів на місці, 
підтримуючи властивість купи через `_sift_up`/`_sift_down` замість повного 
видалення і повторної вставки. Це критично для продуктивності, оскільки таке 
оновлення відбувається після кожного розміщення цифри — O(log n) замість 
лінійного пошуку по всій структурі.

Разом ці дві оптимізації дозволяють `opt` перевершувати звичайний MRV за 
кількістю досліджених вузлів на складних прикладах (наприклад, Everest: 
229 проти 1373 вузлів; Platinum Blonde: 225-240 проти 292 вузлів), хоча 
загальний час виконання не завжди пропорційно кращий через накладні витрати 
на пошук hidden singles на кожній ітерації.


На більшості судоку це дозволяє отримати певні покращення у швидкості та у кількості досліджених вузлів, проте має більше викорристання пам'яті.
